# OAC must ship, shrink, and prove control

OpenAgentsControl is no longer competing with other markdown agent packs so much as with the host tools themselves. By October 2026 every major harness except Aider ships custom subagents, Agent Skills, hooks, MCP and a plan or approval mode, so OAC's original bundle of context-scout, task breakdown, code review, parallel execution and plan-then-approve gating is now table stakes rather than a reason to install anything. Against peer frameworks OAC is small and looks stalled. It has 4,910 stars to Superpowers' ~300k, no release since v0.7.1 on 2026-01-30, star growth down from ~1,000 a month to ~100 in the last five weeks, and a community fork publicly calling upstream "unmaintained". The internal audit adds a credibility problem on top. The README advertises commands and docs that do not exist and an npm package that returns 404, approval gates are mostly prompt text, and behavioral evals have not run since a failing January result. OAC does still have assets the leaders lack or execute poorly: a permission-aware canonical build with fail-closed degradation, a "controlled and token-efficient" reputation that users explicitly chose over oh-my-opencode, and a curated standards system that can be repositioned around project-specific conventions. The path forward is to fix the credibility gaps within weeks, stop maintaining features the hosts now provide, and spend effort on the three things hosts leave open: mechanically enforced gates, cross-host builds of portable skills, and published evals that show OAC helps.

## Hosts now ship most of what OAC was built to add

The core of OAC's value proposition, delegating to specialist subagents behind an approval gate with curated context loaded on demand, is now built into the hosts. Claude Code subagents support `tools`, `disallowedTools`, `permissionMode` (including `plan`), `isolation: worktree`, `background: true` and per-agent persistent memory, and plugins can bundle skills, agents, hooks, MCP and LSP servers, monitors and workflows ([Claude Code sub-agents](https://code.claude.com/docs/en/sub-agents); [plugins reference](https://code.claude.com/docs/en/plugins-reference)). Hooks cover **33 lifecycle events** and five handler types, including `prompt` (a single-turn LLM check) and `agent` (a tool-using verifier) ([Claude Code hooks](https://code.claude.com/docs/en/hooks)). OpenCode ships a Plan primary agent with edits and bash set to `ask`, plus built-in Explore and Scout subagents. Scout is a read-only researcher for external docs and dependencies, which is close to OAC's `externalscout` ([OpenCode agents](https://opencode.ai/docs/agents/)). Codex, Cursor and Copilot CLI each ship a built-in explorer agent. Codex adds "Auto-review", which routes sandbox-boundary approvals through a reviewer agent. Copilot ships plan mode and a code-review agent, and Cursor runs parallel subagents in per-agent worktrees or cloud VMs ([Codex docs index](https://learn.chatgpt.com/llms.txt); [Cursor subagents](https://cursor.com/docs/context/subagents); [Copilot CLI](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/use-copilot-cli)).

Formats have converged as well. Agent Skills (a SKILL.md folder with `name` and `description`) lists **40+ clients**, including Claude Code, Codex, Gemini CLI, OpenCode, Cursor, Copilot, Amp, Goose and Factory ([agentskills.io](https://agentskills.io)). AGENTS.md, now stewarded by the Linux Foundation's Agentic AI Foundation, is used by **60k+ projects** and 23 named tools. Claude Code is the notable absentee and still uses CLAUDE.md ([agents.md](https://agents.md)). Hosts increasingly read each other's directories: OpenCode loads skills from `.claude/skills/` and `.agents/skills/`, and Cursor loads subagents from `.claude/agents/` and `.codex/agents/` ([OpenCode skills](https://opencode.ai/docs/skills/); [Cursor subagents](https://cursor.com/docs/context/subagents)). Custom slash-command files are being folded into skills. Claude Code says "Prefer `skills/` for new plugins", and Codex has deprecated Custom Prompts ([plugins reference](https://code.claude.com/docs/en/plugins-reference); [Codex index](https://learn.chatgpt.com/llms.txt)). Subagent frontmatter is the one layer that still diverges: Claude Code uses camelCase permission fields, OpenCode uses `mode`/`permission`/`steps`, Gemini uses snake_case limits, Cursor uses `readonly`/`is_background`, and Codex uses TOML with `developer_instructions` ([Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents); [Gemini CLI subagents](https://geminicli.com/docs/core/subagents/)). That remaining incompatibility is where a translator such as OAC's build still earns its keep.

The host market has also moved away from OAC's home base. In the Stack Overflow 2026 survey, **65.5% of AI-agent users use Claude Code**, against 58.7% for Copilot and 29.5% for Codex ([SO 2026 AI agents](https://survey.stackoverflow.co/2026/ai/data/ai-code-agent)). JetBrains' 2026 data, which reached this research only through secondary summaries, puts Codex's "main tool" share at 16% by mid-year, up from 3% in January ([JetBrains Research](https://blog.jetbrains.com/research/2026/08/18/ai-coding-agent-adoption-2026)). Gemini CLI's consumer users were moved to the closed Antigravity CLI in June 2026, and Roo Code was sunset ([Google Developers Blog](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/); [Kilo vs Roo](https://kilo.ai/kilo-code/vs/roo-code)). OpenCode remains strategically important as the open-source base that Kilo now builds on. Even so, an OpenCode-first framework addresses a far smaller audience than a Claude-Code-first one, and the GitHub description still says only "built for OpenCode" ([GitHub repo](https://github.com/darrenhinde/OpenAgentsControl)).

Commentators argued as early as December 2025 that native Plan Mode, explore subagents and worktree-parallel agents absorb "about 80%" of what heavy scaffolding frameworks offered. They left compliance deliverables, domain templates, tool-agnostic workflows and per-action approval as the remaining niches ([paddo.dev](https://paddo.dev/blog/external-scaffolding-era-ending)). That last item matters for OAC. Per-action approval is literally what the "Control" in its name promises, but OAC currently delivers it mostly through prompt text. The audit section below covers this.

## Peers that won went multi-host through marketplaces; OAC stayed put

By GitHub stars on 2026-10-16, the field is led by Superpowers (**300,412**), ECC (280,966), spec-kit (141,507) and gstack (136,640). Ruflo, OpenSpec, OmO, BMAD and oh-my-claudecode each sit between 40k and 75k, and OAC's **4,910** stars place it below every significant competitor except cc-sdd and Agent OS ([obra/superpowers](https://github.com/obra/superpowers); [github/spec-kit](https://github.com/github/spec-kit); [darrenhinde/OpenAgentsControl](https://github.com/darrenhinde/OpenAgentsControl)). Star counts measure attention, not use. One repo-mining study of 2,853 repos found only 5.5% use a skill and 4.6% a custom subagent, so framework users of any brand are a power-user minority ([buildthisnow summary](https://www.buildthisnow.com/blog/real-examples/state-of-claude-code-2026)). Whether Superpowers' and ECC's 300k-scale counts, both reached within about a year, reflect organic use was not investigated. Release cadence is less ambiguous. Spec-kit shipped 40 releases in the last 90 days, Compound Engineering 33, oh-my-claudecode 20 and OpenSpec 12, while OAC shipped none and its default branch had zero commits in April–June and again in August–October ([GitHub commits API](https://api.github.com/repos/darrenhinde/OpenAgentsControl/commits)). The unreleased `refactor/canonical` work (tiered install, profile installs, doctor) is invisible to users. A 0-star fork created 2026-10-01 already advertises itself as "Community fork (active development). Upstream is unmaintained" ([apilot fork](https://github.com/apilot/OpenAgentsControl)).

The winners share a pattern that OAC has not matched. Superpowers is listed in both Anthropic's official Claude marketplace and OpenAI's Codex marketplace, supports **16 hosts**, and bootstraps through a SessionStart hook or, where a host has none, through a skill description ([Superpowers README](https://github.com/obra/superpowers); [v7.0.0 notes](https://github.com/obra/superpowers/releases/tag/v7.0.0)). BMAD v7 is moving off its own npx installer onto `npx skills add` and the Claude Code and Codex marketplaces ([BMAD README](https://github.com/bmad-code-org/BMAD-METHOD)). wshobson/agents is the closest structural analogue to OAC's canonical build. It turns one shared markdown source into artifacts for **7 harnesses**, including Codex TOML agents with oversized skills split to fit Codex's 8 KB budget, and publishes a per-harness capability matrix ([wshobson/agents](https://github.com/wshobson/agents)). OAC's build emits only OpenCode agents and `registry.json`. The Claude Code agents are staged to `.tmp/oac-build/` and compared rather than emitted, and skills and commands are not built at all (`packages/cli/src/commands/build.ts`; `packages/compatibility-layer/src/core/BuildPipeline.ts:77`). OAC's distinctive engineering asset is therefore behind on breadth against a competitor that ships the same idea.

The projects that stalled are instructive. SuperClaude (no release since March, plugin system still "planned"), Task Master (needs its own API keys and an MCP runtime, last push April) and Agent OS (no release since January) were mostly Claude-Code-only, slash-command-era, or dependent on a separate runtime. GSD was archived and relaunched as GSD Core, oh-my-opencode left OpenCode for its own pi fork, and claude-flow rebranded as Ruflo ([SuperClaude](https://github.com/SuperClaude-Org/SuperClaude_Framework); [Task Master](https://github.com/eyaltoledano/claude-task-master); [GSD archived README](https://github.com/gsd-build/get-shit-done); [oh-my-openagent](https://github.com/code-yeongyu/oh-my-openagent)). The survivors re-platformed onto skills and marketplaces and encoded an opinionated method rather than duplicating native plumbing. Those methods include TDD that deletes code written before tests (Superpowers), spec deltas merged on archive (OpenSpec), learning loops that write lessons back into the repo (Compound Engineering, ECC), right-sized routing that sends small changes straight to build (BMAD, Superpowers v7, cc-sdd), and org presets that enforce standards (spec-kit) ([OpenSpec](https://github.com/Fission-AI/OpenSpec); [Compound Engineering](https://github.com/EveryInc/compound-engineering-plugin); [cc-sdd](https://github.com/gotalab/cc-sdd)). OAC has the raw material for several of these but ships none as a feature.

The departure of oh-my-opencode leaves an opening. The biggest OpenCode-native rival has left OpenCode, and OpenCode v2, which breaks v1 plugins, renames config keys and turns permissions into an ordered array, opened its upgrade path on 2026-10-12 ([OpenCode v2 migration](https://opencode.ai/v2/docs/migrate-v1/); [AICoder](https://aicoder.com/news/news-20261012-opencode-2-upgrade-path-v1-19)). Migrating OpenCode users need a v2-native framework, and that window is open now. OAC's issue tracker already shows the cost of missing it: #349 (`"*": "deny"` hides tools under current OpenCode), #362 (v2 profile names displayed wrong) and #367 (port to the v2 plugin API) are all open ([OAC issues](https://github.com/darrenhinde/OpenAgentsControl/issues)).

## The README promises more than the code delivers

The audit of `refactor/canonical` (HEAD `d7924e4`) found that docs have drifted from the code in ways users hit on day one. The README tells Claude Code users to run `/oac:setup --core` and advertises `/oac:plan`, but neither command exists. It links `FIRST-TIME-SETUP.md` and `QUICK-START.md`, which do not exist, and it claims "9 workflow skills" where there are 12 (`README.md:189-226`; `plugins/claude-code/`). Issue #281, reporting `/oac:setup` as an "unknown skill" after install, has been open since March with no reply ([#281](https://github.com/darrenhinde/OpenAgentsControl/issues/281)). That is the cheapest growth channel, a working marketplace install, failing silently. The README's recommended install, `npm i -g @controlstack/oac`, returns **404**. The only published package is `@nextsystems/oac` at 0.7.0. `VERSION` and the manifests say 1.1.0 on the branch, yet the CHANGELOG stops at 0.7.1, no 1.x tag exists, three automated v0.7.2 bump PRs are open, and ROADMAP.md, last updated December 2025, still lists Claude Code support as "Next" (`VERSION`; `CHANGELOG.md`; `ROADMAP.md`).

Several headline claims do not survive measurement. "Context files <200 lines" is false for **82 of the 297** context files. The "80% reduction" token claim has no benchmark anywhere in the repo. "Any language" drew issue #283, which noted that OAC is tied to JS frontend work in practice, and "Model agnostic" is a property inherited from OpenCode, since the Claude plugin pins `opusplan` (`README.md:77,95`; `plugins/claude-code/settings.json`; [#283](https://github.com/darrenhinde/OpenAgentsControl/issues/283)). The community now actively polices this kind of claim. Ruflo's own audit found headline multipliers were "hardcoded doc strings with no benchmark", and an awesome-claude-code issue called its token-savings figure fabricated ([ruflo audit](https://github.com/ruvnet/ruflo/blob/main/docs/reviews/intelligence-system-audit-2026-05-29.md); [awesome-claude-code #1338](https://github.com/hesreallyhim/awesome-claude-code/issues/1338)). Unbenchmarked percentages are now a liability, not marketing.

The "Control" promise is the most consequential gap. On OpenCode, OpenAgent's `bash: "*": "ask"` and its edit-deny globs for secrets are real host enforcement. OpenCoder, however, has no catch-all bash rule, and the "Request approval before ANY execution" stage flow is prompt text (`content/agents/core/openagent.md`; `content/agents/core/opencoder.md`). On Claude Code the plugin ships no permission rules. The `coder-agent` deliberately widens edit scope, the five deny globs live in a copy-paste `RECOMMENDED-PERMISSIONS.md`, and approval is a skill injected by a SessionStart hook (`plugins/claude-code/RECOMMENDED-PERMISSIONS.md`; `plugins/claude-code/hooks/hooks.json`). The README's "Agents ALWAYS request approval before execution" therefore overstates what happens on OpenCoder and on Claude Code. One reviewer has already framed Propose → Approve → Execute as added latency ([Bright Coding](https://www.blog.brightcoding.dev/2026/08/01/darrenhindeopenagents-ai-code-generation-that-learns-your-patterns)).

Quality claims rest on tests that cover packaging, not behavior. The deterministic layers are solid: 553 compat-layer and 226 CLI unit tests pass locally, `oac build --check` reports no drift, and installer e2e and five profile smoke tests pass on Ubuntu and macOS. The behavioral eval framework, however, is OpenCode-only and grades tool-call paths. Its scheduled workflow sits in `.github/workflows/evals/`, a subdirectory GitHub Actions never loads, and the last stored result (`evals/results/latest.json`, 2026-01-17) records 0 of 1 passing, with "missing-approval" and "execution-before-read" violations. PR #342 itself was red on the last push. A profile-reference floor test and a vitest advisory both failed, and the two local unpushed commits (`a4c8ab3`, `d7924e4`) fix exactly those failures. Smaller inaccuracies compound the impression. The comment in `build.ts` still says all 7 Claude files "would change" while the build reports them identical, a golden test stays skipped, `CapabilityMatrix.ts:319` carries a FIXME for a non-existent concept, skills are scattered across three directories (one of which is excluded from the npm `files` list), and install profiles use three separate vocabularies across the bash installer, the CLI and `install-context.ts`.

User reports line up with these internal findings. Install failures dominate the issue tracker: #237's missing `paths.json` drew at least five "same problem" reports, alongside a Windows failure (#304) and a request for a clean uninstall (#266). Issue #258 reports GPT models taking "upwards of 10 minutes" to find OAC context while vanilla plan/build mode is fast ([#237](https://github.com/darrenhinde/OpenAgentsControl/issues/237); [#258](https://github.com/darrenhinde/OpenAgentsControl/issues/258)). Unclosed spam and bot "auto-sync" issues (#278, #282, #289, #293) signal light triage to anyone deciding whether the project is alive.

## Research favors enforcement and evals over more context

The evidence on context engineering undercuts OAC's most prominent mechanism as currently framed. Anthropic's guidance is "the smallest set of high-signal tokens", with just-in-time retrieval and subagents that return condensed summaries ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Controlled 2026 studies find that context files **do not generally improve task success** and raise inference cost by more than 20%. Repository overviews did not help, and the value lay in documenting non-standard practices ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)). A 291-run study of Claude Code and Codex found no correctness difference between no context, an always-on AGENTS.md and selective on-demand delivery. Selective delivery did cut Claude's cache-creation tokens on 11 of 11 tasks, and the study found failures came from implementation skill rather than missing repo facts ([arXiv 2607.27250](https://arxiv.org/html/2607.27250v1)). A 1,650-session factorial study found that file size (25–500 lines), position and multi-file splitting had **no detectable effect on compliance**. The dominant effect was within-session decay of about 5.6% lower odds per generated function, with a median first omission at function 4 ([arXiv 2605.10039](https://arxiv.org/pdf/2605.10039)). For OAC the conclusion is direct. Lazily loading generic TypeScript or security best practices that frontier models already know will not raise quality. The real case for lazy loading is tokens and latency, which issue #258 suggests OAC is currently making worse. Rules that must hold need hooks, linters or verifier agents, because restating them does not keep the model compliant.

Prompt style is a second risk. Anthropic's prompting guidance reports that Claude models from 4.5 onward over-trigger on "CRITICAL: You MUST" phrasing and recommends conditional "use X when Y" wording ([Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), seen via a secondary summary). OAC's `using-oac` skill ("requiring Skill tool invocation BEFORE ANY response… secret weapon") is exactly that pattern. It is injected every session, and it competes with the host's own skill policy. IFScale found even the best of 20 models reached only 68% adherence at 500 simultaneous instructions, with a bias toward earlier ones ([arXiv 2507.11538](https://arxiv.org/html/2507.11538v1)). Stacked mandatory flows (approach, then context discovery, then task breakdown) should therefore be expected to lose their later steps. No controlled study has yet isolated "MUST invoke skill" coercion, so this is a strong inference rather than a measured result.

The harness is a measurable variable, which is both a threat and an opportunity. In a 66-configuration study, model rankings reversed across harnesses. Claude led GPT by 7.94 points under OpenHands and trailed by 30.16 under PI, and cost did not track score ([arXiv 2610.00917](https://arxiv.org/html/2610.00917v1)). A harness survey reports prompt, middleware and verification changes alone moving Terminal-Bench 2.0 from 52.8% to 66.5% with the model held fixed ([arXiv 2606.20683](https://arxiv.org/pdf/2606.20683), snippet-level source). A harness layer can therefore plausibly add value, but only measurement shows whether a particular layer does. Anthropic's eval guidance gives the recipe: start with **20–50 tasks drawn from real failures**, grade outcomes rather than tool-call paths, isolate trials, use pass^k for consistency, and separate capability suites from regression suites ([Anthropic, Demystifying evals](https://anthropic.com/engineering/demystifying-evals-for-ai-agents)). Detecting a 10-point effect needs roughly 120–200 tasks ([arXiv 2607.27250](https://arxiv.org/html/2607.27250v1)). Harbor, from the Terminal-Bench team, already runs containerized trials with built-in Claude Code, Codex, OpenHands and Aider agents ([VentureBeat](https://venturebeat.com/ai/terminal-bench-2-0-launches-alongside-harbor-a-new-framework-for-testing)). OAC's existing evaluators ("did it call context-scout first") are the brittle path-grading Anthropic warns against. They belong in a regression suite, not as the proof of value.

Supply-chain risk shapes how a context registry should ship. The ClawHavoc campaign planted 1,184+ malicious skills in OpenClaw's ClawHub between February and May 2026, and the Cloud Security Alliance notes that code scanners miss the semantic attack surface. Evasive skills persisted even after VirusTotal screening was added ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-skill-supply-chain-attacks-20260624-csa/); [Unit 42](https://unit42.paloaltonetworks.com/openclaw-ai-supply-chain-risk/)). OAC's context files are injected into model instructions just as skills are, and `install-context.ts` sparse-clones them from GitHub. The recent move to manual registry updates is correct. Pinned versions, checksums and least-privilege subagents (read-only scouts, scoped writers) should follow, and they double as a governance pitch to teams.

## OAC can still credibly own "controlled, portable, proven"

Three assets are defensible if OAC invests in them. The first is the **canonical build**. Its last-match-wins permission model with fail-closed degradation (`packages/compatibility-layer/src/core/Capabilities.ts`) is more rigorous than translating permissions by template, and it is the right foundation for the one format layer hosts have not converged on, subagent frontmatter and permissions. It needs breadth: skills and commands under `content/`, spec-compliant SKILL.md output (host-specific keys under `metadata`, as OpenCode's docs prescribe), an AGENTS.md emitter, and a Codex TOML target. Cursor comes nearly free because it reads `.claude/agents/`. The documented blocker, that hosts with only binary permissions cannot express scoped rules, should be published as a capability matrix rather than hidden. Making the gaps explicit is itself a trust signal, and wshobson shows the format.

The second asset is **control as a mechanism rather than a prompt**. Claude Code's PreToolUse and PermissionRequest hooks, with `prompt` and `agent` handlers, let a plugin enforce what OAC currently only asks for: deny edits to `.env`, keys and `.git`, require a plan artifact before writes, and run a verifier agent before "done" ([Claude Code hooks](https://code.claude.com/docs/en/hooks)). Hooks reach where plugin permission rules cannot, so this is the honest fix for the `RECOMMENDED-PERMISSIONS.md` workaround. It is also the gap commentators left open when they said hosts absorbed most of the scaffolding market ([paddo.dev](https://paddo.dev/blog/external-scaffolding-era-ending)). Users already credit OAC with this positioning. In Discussion #116 they left oh-my-opencode over token burn, and the maintainer framed OAC around "repeatable behaviour" for teams ([Discussion #116](https://github.com/darrenhinde/OpenAgentsControl/discussions/116)). Right-sizing has to accompany it. Gates should fire on risk (writes outside scope, destructive bash, secrets) and not on every step, which answers the latency critique.

The third asset is the **standards system, repositioned**. Hosts provide containers, and their Explore agents search code, not curated standards. The research says the content that helps is project-specific and non-inferable. OAC's context system should therefore pivot from shipping 61k lines of mostly generic guidance across 297 files, 108 of which are internal documentation about OAC itself, toward three jobs. It should discover a project's actual conventions from its code, as Agent OS does. It should emit them into AGENTS.md and nested files within host budgets such as Codex's 32 KiB default ([Codex AGENTS.md guide](https://developers.openai.com/codex/guides/agents-md.md)). And it should write lessons back after each task, the learning loop driving Compound Engineering and ECC. Team presets with required installs, which spec-kit and gstack both ship, fit the "made for teams" claim. All of this needs an ablation, OAC off vs lite vs full, before any number appears in the README.

A steelman for the opposite strategy deserves a hearing. OAC could abandon multi-host ambitions and become the best OpenCode v2-native framework, betting on the open-source host that Kilo builds on and that oh-my-opencode vacated. That plan is cheaper and time-sensitive. But it concentrates OAC on a minority host, and v2 has already shown that single-host add-ons absorb every breaking change. The better plan is to ship the v2 port first because the window is open, while making the build, not any single host, the long-term product.

## Conclusion

The question has shifted from "which framework has the best agents" to "which layer earns its tokens on top of a host that already has agents". On that test, OAC's most visible features, scouts, task managers and approval prompts, are the least defensible. Its least visible ones, the fail-closed permission translator and the habit of treating context as curated standards, line up with the gaps the research leaves open: enforcement that survives within-session decay, portability across diverging frontmatter, and evidence that a harness layer helps. The project's name already promises control. What it lacks is mechanisms, measurements and releases that let outsiders verify the promise.

The binding constraint is attention, not ideas. Competitors ship weekly with teams or company backing, so a solo-maintained OAC cannot win on breadth of catalog or host count by brute force. It can win a narrower claim that few peers bother to prove: that OAC makes agents measurably safer and no slower, on whichever host you use. Every item in the plan above either removes a reason to doubt that claim or produces evidence for it, and anything that does neither belongs in the "stop" column.
